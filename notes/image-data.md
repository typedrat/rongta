# R22 image data

Evidence: RONGTA 3.1.6 (1028), protocol/ODM 28, ARM64 SDK SHA-256
`4bbef7e782ac6ef37b758cba7aadf61ca29ad957870e3c5f96e23de5efd44695`.
`tests/fixtures/sdk/image.json` contains 19 original-SDK cases: seven ARGB
conversions plus 12 packed-raster jobs. One case records a native defect that
Rust rejects. All other jobs match byte-for-byte and independently decompress
to their source rasters. These are emulator-generated bytes, not printer captures.

## Pixels to raster

The traced R22 image-entry screen selects algorithm 0 and threshold 208.
The JNI API consumes row-major ARGB bytes; internally the SDK converts them to
RGBA, ignores alpha, and computes:

```text
gray = truncate(green * 0.59 + red * 0.3 + blue * 0.11)
black = gray <= threshold
```

The operation order and double-precision truncation matter at boundaries: this
is not the `image` crate's standard luma conversion. Each row packs left to
right, MSB first, with 1 = black. The reference cases include grayscale ramps,
colors, alpha changes, and asymmetric dots to establish bit and row order.
`rgb2PrintData(..., algorithm=0, invert=0)` provides independent raster output;
`getImagePackageData(..., model=255)` accepts a prepacked raster, isolating the
compressor from conversion. Algorithm 0 jobs use the same compression.

Rust's `Raster::from_rgba` matches native conversion but safely pads partial
rows to the next eight dots. The native code allocates floor(width*height/8)
bytes while packing ceil(width/8) bytes per row; unaligned dimensions are unsafe
in the SDK and are not exercised through JNI. The CLI composites alpha onto
white first, matching the app's white-canvas preparation. It does not resize,
crop, rotate, dither, invert, or apply physical offsets.

## Huffman sections

`getAllCompressImagePart` (`0x14695c`) initially tries all remaining raster bytes
as one section. `RTGetHfmTree` (`0x128440`) counts byte
frequencies; leaves are inserted in ascending byte order. For a one-symbol
raster it appends a dummy leaf of weight 1: symbol+1 below 128, otherwise
symbol-1. It repeatedly combines the two lightest unparented nodes. Equal
weights choose the earliest inserted node. The first selected node is the left
child (bit 0); the second is the right child (bit 1). Internal nodes receive
successive names 256, 257, … in construction order.

`getTreePack` serializes every node name as little-endian u16, first preorder,
then inorder. For N leaves this is 4*(2*N-1) bytes. There is no additional tree
header. The serializer requires tree_bytes < pBuffLength-25. If it does not fit,
the native section length is halved and rounded down to a whole number of rows,
then the tree is rebuilt. After emitting that section, it repeats with all
remaining rows. Packet indices restart at zero for each section.

Rust uses a standard-library heap ordered by (weight, insertion index), plus
Deku's bit-vector types. A generic canonical-Huffman encoder would assign
different codes and would not provide the required named-node traversals.
The implementation needs no additional compression dependency.

## Packet grouping and layout

All frames use cleartext mode 0, message type 1, superclass 5:

| Subclass | Subtype | Payload |
| --- | --- | --- |
| `0b` | 1 | Empty; image start |
| `0e` | 1 | Section's tree traversals |
| `0d` | **0** | Packet header and compressed bits below |
| `0c` | 1 | Empty; image end |

`getPrintImageOnePackageWithImageWidthByte` computes a peculiar budget:

```text
hint = floor((pBuffLength - 36) / byte_width)
if hint <= 11: hint = byte_width * byte_width * 10
hint = min(hint, section_raster_bytes)
bit_limit = hint * 8 - 8
```

`RTHFMDGencoding` accumulates whole rows while the sum of their Huffman code
lengths is strictly less than `bit_limit`. On equality or overflow it begins
another packet. Preserve these units; substituting a generic MTU-sized chunker
would change SDK output.

`05/0d` payload:

| Offset | Type | Meaning |
| --- | --- | --- |
| 0 | u16 LE | Packet index within section |
| 2 | u16 LE | Remaining payload bytes (payload length minus 4) |
| 4 | u8 | `11` hex, compression format marker |
| 5 | u16 LE | Raster byte width |
| 7 | u32 LE | Zero |
| 11 | u8 | Unused bits in last byte, 0–7 |
| 12 | bytes | MSB-first Huffman codes |

There is no explicit row count in this payload. The receiver can recover it
from decoded byte count / byte width. At packet boundaries, the native encoder
fills ignored padding bits with the beginning of the **next** packet's codes;
only the final section padding is zero-filled. Rust reproduces this detail.

## Validation and deliberate limits

The encoder checks the entire output against the supplied `pBuffLength` and
requires a buffer of at least 64 bytes. It fails if a tree cannot fit even one
row, avoiding the SDK's zero-length section loop. It also fails if the SDK's
packet arithmetic would create an initial empty packet. The one-byte fixture
shows that defect: the SDK's aliased buffer gives the empty packet a padding
count of 7 despite having no compressed bytes. Rust does not reproduce it.
Oversized packet indices, byte widths, and wire payload lengths are rejected.

Tests cover singleton trees, all 256 symbols, ties, skewed frequencies,
byte-unaligned packet boundaries, multiple packets, repeated tree sections,
and arbitrary rasters decoded through an independently written traversal
reader. CRC/framing tests remain separate. File decoding uses the `image`
crate's PNG/PNM support and a 64 MiB decoder allocation limit.

The output is the native image-data job, not the entire app print transaction.
Copies, heat/density, optional metadata, feed, pacing, and print-completion
status still belong to the surrounding session. Neither this encoder nor the
SDK fixtures establish which parameters the physical R22 reports or whether
it has accepted/printed a job. Run `info` for its buffer and width, then capture
a tiny stock-app print before choosing those surrounding commands and timing.
